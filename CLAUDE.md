# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Quantrade is a personal quant portfolio bot ("분석, 추후엔 자동 거래" — analysis now, autotrading later). It scans Korean crypto (Upbit) and US stocks, asks Claude for buy/sell/hold decisions, executes small/low-risk trades automatically, and queues larger or riskier trades for manual approval via Telegram. State lives entirely in JSON files committed to the repo; GitHub Actions is the runtime (there is no server).

There are no tests, no linter config, and no dependency manifest (`requirements.txt`) in this repo — the only third-party dependency is `requests`, installed inline in CI (`pip install requests`). When changing code, mirror that: keep dependencies minimal and don't introduce a build/test toolchain unless asked.

## Project context

- This is a personal AI investment-decision *assistant*, not an autotrader — every non-trivial trade is either auto-executed under tightly bounded safety rules or held for explicit human approval via Telegram. Do not blur that line.
- The user is doing mandatory military service and only has PC access ~6-9am at a "cyber knowledge information room" (사이버지식정보방); the rest of the time they interact via the mobile Claude app. Code changes now happen through Claude Code. Keep this in mind for anything time-sensitive (e.g. don't assume same-day follow-up is possible outside that window).
- The project is in a validation/trial phase running through December 2026 — this is a virtual simulation with no real trades yet. Expanding to real trading is only to be discussed after backtest validation, not implemented unprompted.
- Asset coverage is actively transitioning from crypto (Upbit) to domestic Korean stocks via the Toss Securities API, because crypto exchange sites are blocked on the military network. Expect `analyze_lib.py`'s crypto-scanning code to be gradually replaced/supplemented by Toss-based stock scanning — when working here, check whether the crypto path is still the active one or already superseded.
- Overall project direction/roadmap lives in a separate planning document outside this repo; ask the user for it if you need it rather than assuming.

## Running

```bash
pip install requests
export TELEGRAM_TOKEN=...      # bot token
export TELEGRAM_CHAT_ID=...    # chat to notify
export CLAUDE_API_KEY=...      # Claude API key for trade decisions
python analyze.py          # run one full daily analysis/trade cycle
python check_updates.py    # poll Telegram for /approve /reject /keep /unkeep /status commands
python backtest.py         # run the backtest engine against historical data (see below)
```

Both `analyze.py` and `check_updates.py` read and rewrite the JSON state files in the repo root, then (in CI) those files are committed back. There's no test suite to run — verify changes by running the script locally against the existing JSON state and inspecting the diff/output, or by mocking `requests` calls if testing logic in isolation.

## Session start checklist

- **Check `main`'s latest commit log before assuming you know the repo's state.** Multiple sessions (this repo is worked on in parallel from different Claude Code sessions) can merge to `main` between your sessions — a branch/PR that was "still just a scaffold" or "not yet implemented" last time you looked may not be anymore (this happened 2026-08-01: `real_portfolio_sync.py` went from a `NotImplementedError` stub to a real, working read-only Toss sync in a parallel session, and it wasn't caught until a later session diffed against `main`). `git fetch origin main && git log --oneline origin/main -10` before relying on anything this file says about current implementation state.

## Architecture

**`analyze_lib.py`** — all shared logic and I/O: technical indicators (MA, RSI, Bollinger bands), Upbit/Yahoo/stooq/Naver market data fetchers (including `get_krx_candles`, a Naver-based historical fetcher for Korean stocks used until the Toss Securities API is wired in), the shared entry-scoring rule (`entry_score`, used by both live scanning and the backtest engine so they can't drift apart), crypto/stock candidate scanning (`scan_crypto`, `scan_stocks`), Google News RSS sentiment scoring (`get_news_sentiment`), the Claude API call that turns holdings + candidates + news into a decision JSON (`ask_claude_decision`), Telegram sending, and generic `load_json`/`save_json` helpers. Constants here (`HARD_STOP_LOSS`, `EXCLUDE_MARKETS`, `US_STOCKS`, `TRADING_COSTS`, sentiment word lists, `TRACK_B_ENABLED`) are the tunable knobs for strategy behavior. `ask_claude_decision` takes an optional `real_positions` list (symbol/name/quantity/current_price/return_pct only — never account numbers) and instructs Claude to prefix any real-account decision's `market` field with `REAL:` so `analyze.py` can route it without colliding with virtual-portfolio market strings of the same ticker (e.g. `NVDA` exists in both `US_STOCKS` and the user's real holdings).

**Phase 2 news-events work exists but is deliberately *not* wired into the live decision flow.** `entry_score` (RSI + Bollinger) still gates which candidates `scan_crypto`/`scan_stocks` surface each day — kept for practical reasons (the full ~80-market crypto universe can't all be sent to Claude daily) — and its docstring now frames it as a pre-filter rather than a trading thesis, but `ask_claude_decision` itself still runs on the original `get_news_sentiment` keyword-count + unmodified prompt, exactly as before Phase 1's gate failed. A same-day attempt to replace `get_news_sentiment` with `get_news_headlines` (raw headline text passed straight into the prompt, with an explicit "price metrics aren't the basis, news events are" instruction) was built and merged, then **reverted** within hours: shipping an unvalidated prompt/judgment change straight into the real approval flow (even with Track B disabled, this still drives what a human sees and acts on via Telegram) violated the "safety nets and approval criteria don't change before validation" principle. `get_news_headlines`/`_format_news` are kept in the file (not deleted) as a standalone, disconnected utility for future experiment scripts — event-type classification (실적발표/공시/M&A/규제) and the KRX-only scope for that work are still to be designed, and reconnecting it to `ask_claude_decision` is an explicit separate decision gated on calibration results, not something to do inline. `HARD_STOP_LOSS` was never touched by any of this — it's the one AI-independent, unconditional safety net the eventual news-driven design is modeled after.

`get_us_closes` tries Yahoo Finance's chart API first, then falls back to stooq — stooq alone was confirmed (during the phase-1 backtest run) to return a bot-detection challenge page instead of CSV from GitHub Actions IPs, which meant `scan_stocks` had likely been silently finding zero US stock candidates in every daily run (no `asset_class: "stock"` entries ever appear in `portfolio.json`/`trade_history.json`). This edit could not be network-tested in the editing sandbox (all outbound hosts were proxy-blocked there) — confirm it actually works by checking `daily.yml`/`backtest.yml` logs after this lands, and add another fallback if Yahoo also turns out to be blocked from Actions IPs.

**`analyze.py`** — the daily cycle (`run()`), driven by `daily.yml`:
1. Price every held position, compute return %.
2. Scan for new crypto/stock candidates, classify each by expected holding period into a strategy: 단타 (day, ≤6 days), 스윙 (swing, ≤20 days), 장기 (long-term, >20 days) — see `classify_strategy`/`estimate_holding_period`.
3. Send all holdings + candidates + news to Claude (`ask_claude_decision`) for a market summary and per-market decisions.
4. Apply decisions:
   - Hard stop-loss (`HARD_STOP_LOSS` per strategy type) always fires immediately regardless of AI decision.
   - Otherwise, a sell/buy either executes automatically or goes into `pending_actions.json` awaiting Telegram approval, based on `needs_approval()`: 장기 (long-term) positions, `stock`/`krx` asset classes, or positions ≥10% of total assets (`AUTO_TIER_WEIGHT`, `analyze_lib.py`) all require approval; small crypto swing/day trades below that weight execute automatically.
   - **Position sizing / Risk Engine (2026-08-01 design, simulation-only):** two constants in `analyze_lib.py` — `AUTO_TIER_WEIGHT = 0.10` (auto-execute ceiling; a candidate sized at or above 10% of total assets routes to approval instead) and `POSITION_WEIGHT_HARD_CAP = 0.20` (absolute per-position ceiling — even a Telegram-approved buy is clamped down to 20% of total assets if the AI-suggested weight exceeds it, with a warning line in the report). `MIN_CASH_RESERVE_RATIO` (in `analyze.py`) was raised 0.2 → 0.3, i.e. total risk-asset exposure is capped at 70% instead of 80%, in response to the Phase 1 backtest gate not passing. Fixed alongside this: `min_cash` is now computed as `total_assets * MIN_CASH_RESERVE_RATIO` (live current total assets), not the old fixed `TOTAL_BUDGET` — previously the cash reserve didn't grow or shrink with the portfolio's actual size, which defeated the point of a *ratio*. **This entire mechanism (`needs_approval()`, the auto-tier, the hard cap) only ever touches `portfolio.json`, the simulation state `analyze.py`/`check_updates.py` read and write.** `real_portfolio_sync.py` (see below) now does real, working **read-only** account syncs (PR#7/#8) — a factual update from this constant's original 2026-08-01 design note, which described it as a `NotImplementedError` stub; it no longer is. Real-account sell/rebalance suggestions (`TRACK_B_ENABLED`, see below) never go through `needs_approval()`/the auto-tier at all and always require approval unconditionally — but that gate is *not* the same thing as "Track B" as strictly defined further down (order-execution code + an automatic trigger, neither of which exist); flipping `TRACK_B_ENABLED` alone doesn't satisfy either criterion.
   - The `conviction: true` flag has no interaction with any of the above — it's only ever set post-buy via the `/keep` Telegram command, and is only checked in the sell-decision loop (to skip automated sell/hold for pinned positions). It cannot be used to route a buy around `AUTO_TIER_WEIGHT`/`POSITION_WEIGHT_HARD_CAP`, since those checks happen at buy time, before any position (and thus any conviction flag) exists.
5. Persist `portfolio.json`, `trade_history.json`, `pending_actions.json`, and a dashboard-facing snapshot `last_report.json`, then send the report text to Telegram.

**Real-account suggestion gate (`TRACK_B_ENABLED`, 2026-08-01) — narrower than, and not the same thing as, "Track B" below.** "Track B" (further down) is strictly defined as real-money *auto-trading*: order-execution code plus an automatic trigger, both currently absent. `TRACK_B_ENABLED` only controls whether AI-generated **suggestions** on real holdings are labeled dry-run — nothing it gates ever places an order, and turning it on doesn't move either Track B criterion to true. The name collision is unfortunate (both trace back to the same "Track B" term in the user's external planning doc) but the two are genuinely different mechanisms; don't conflate "the suggestion gate is on" with "Track B is active" in either direction. `real_portfolio_sync.py` is a working read-only sync against the official Toss Open API (OAuth2 client_credentials → `GET /api/v1/accounts` → `/holdings` → `/buying-power` → `/exchange-rate`, hardcoded to the confirmed spec since it's no longer unverified), run manually via `sync_real.yml` (`workflow_dispatch`, commits `real_portfolio.json`). `analyze.py` loads `real_portfolio.json` and passes a stripped-down view (symbol/name/quantity/current_price/return_pct — **never `accountNo`/`accountSeq`**, checked into `real_portfolio.json` in the first place: see State files below) into `ask_claude_decision`, which can propose `REAL:`-prefixed sell/비중조정 decisions for real holdings. `analyze.py` routes any such decision straight into `pending_actions.json` with `target_account: "real"` — **it never runs through `needs_approval()`/the auto-tier; every real-account suggestion requires Telegram approval, unconditionally, with no exceptions.**
- `TRACK_B_ENABLED` (env var, `analyze_lib.py`, default `"false"`) is this gate. While it's `false` (the only state so far), every real-account `pending_actions` entry is written with `"dry_run": true` and its Telegram/report text carries an explicit `[모의]` (mock) tag. `check_updates.py`'s `handle_approve` special-cases `target_account == "real"` **before** the normal sell/buy dispatch: it replies that the gate hasn't passed and does **not** change the action's status (`/approve` is a safe, repeatable no-op) — `/reject` still works normally (dismissing a suggestion is never unsafe).
- **Even with `TRACK_B_ENABLED=true`, nothing executes** — there is no order-placing code anywhere in this repo for the real account (`real_portfolio_sync.py` is deliberately read-only), so `handle_approve` on a non-dry-run real-account action currently just replies that execution isn't implemented. The flag exists so that decision can be made independently of (and after) building actual order execution, not as a stand-in for it — and even once it's on, that still isn't Track B (see above).
- **`TRACK_B_ENABLED` must stay `false` until an explicit gate-passed decision** (per the 2026-08-01 handoff doc, expected around end of October 2026, decided in a claude.ai direction-setting session — not something to flip inline while doing unrelated work). Flipping it currently only removes the `[모의]` label and sets `dry_run: false` in new pending actions; it has no execution effect today, but treat it as a guardrail anyway, per the "confirm before changing safety nets" principle below.

**`check_updates.py`** — the Telegram command loop (`run()`), driven by `poll.yml` every 15 min. Long-polls `getUpdates` since `telegram_offset.json`'s last update id, and handles:
- `/approve <id>` / `/reject <id>` — resolve a pending action from `pending_actions.json`. `handle_approve`/`handle_reject` both branch on `target_account == "real"` first (the `TRACK_B_ENABLED` suggestion gate, see above) before falling through to the normal virtual sell/buy dispatch — a real-account action never reaches the `portfolio.json`-mutating code path.
- `/keep <market>` / `/unkeep <market>` — toggle the `conviction` flag on a held position.
- `/status` — report current positions back to Telegram.

After any state change it also refreshes `last_report.json` (`refresh_last_report`) so the web dashboard reflects approvals immediately rather than waiting for the next daily run.

**`backtest.py`** — Phase 1 backtest engine (계획서 v3 §5), run manually (CLI or `backtest.yml` workflow_dispatch), separate from the daily/poll cycle. **Its entry signal is intentionally decoupled from live scanning** (`scan_crypto`/`scan_stocks`/`entry_score` in `analyze_lib.py` are untouched): after the first RSI+Bollinger-only backtest failed to hold up in validation, the strategy was redesigned around trend-following — a 20/60-day moving-average golden cross gated by ADX ≥ 25 (`is_golden_cross`, `calc_adx` in `analyze_lib.py`) as the main signal, with RSI/Bollinger demoted to an entry-timing filter (skip if RSI ≥ 75 or price already above the upper band) rather than an independent trigger. Don't assume backtest changes here apply to live trading — promoting a backtested rule into `entry_score` is a deliberate, separate step per "전략 검증이 아키텍처보다 먼저다" (validate before wiring into live scanning). Since past Claude decisions can't be replayed (cost + non-determinism), sell-side is still approximated with rule-based exits (hard stop-loss, RSI overbought, a time-stop at 2x the expected holding period) — a known simplification to revisit once Phase 2's AI-confidence calibration exists. Applies `TRADING_COSTS` (fee + slippage assumptions, plus a KRX sell-only `sell_tax_pct` for 증권거래세) on entry/exit, splits trades into a 70/30 train/validation set by date, and buckets results by market regime (상승장/하락장/횡보장, from trailing 60-day return) and by strategy type. Also computes a simple buy-and-hold benchmark over the same instruments/period (`buy_hold_trades`) so the strategy's numbers can be judged against "would just holding have done better" (`benchmark_buy_hold`/`strategy_vs_buy_hold` in the report) — not just against the frozen success criteria. Buy-and-hold trades are also regime-tagged (at entry only, not day-by-day through the multi-year hold) so `by_regime_strategy`/`by_regime_buy_hold` can be compared per regime. Results are checked against the frozen success criteria from 계획서 v3 §4.3 (`SUCCESS_CRITERIA`: ≥30 trades, sharpe-like ratio) and written to `backtest_report.json`. MDD (2026-08-01, updated once the Risk Engine position-sizing design landed): `compute_metrics()`/`group_metrics()` now weight each trade's contribution to the equity curve by `POSITION_WEIGHT` (= `analyze_lib.AUTO_TIER_WEIGHT`, 10%) instead of assuming each trade reinvests 100% of assets — win rate/avg return/sharpe are untouched, only the MDD equity curve changes. This brings MDD down from the old ~-98~-100% (which assumed full-notional sequential reinvestment) to numbers roughly an order of magnitude smaller, closer to what a single 10%-sized position could actually drawdown. **This is a constant 10% scaling factor, not a portfolio-level simulation** — it does not reflect actual concurrent holdings (several positions open on the same dates), diversification/correlation effects across instruments, or the real two-tier cap mix (`AUTO_TIER_WEIGHT`=10% auto-tier vs. `POSITION_WEIGHT_HARD_CAP`=20% human-approved ceiling in `analyze.py` — every trade here is scaled by the same flat 10%, not the blend of sizes a real approval flow would produce). Treat the resulting MDD numbers as a reference-only *directional improvement* over the old unweighted figure, never as an absolute drawdown estimate to quote on their own — `MDD_CAVEAT` in `backtest.py` states this explicitly and is included in every generated report's `mdd_caveat`/`gate.mdd_reference_only` fields. Per the plan, the ≥30-trade/sharpe thresholds are fixed on purpose and shouldn't be adjusted after the fact to fit results. `evaluate_gate()` bundles the full pass/fail check from the 2026-08-01 handoff doc's §2.1 gate (≥30 trades each split, validation sharpe ≥1.0, train/validation same-sign sharpe as an overfitting check, beats buy-and-hold on both splits — MDD is reported but excluded from pass/fail per its own reference-only caveat) into `report["gate"]`. `--max-hold-multiplier`/`--rsi-exit` override the exit rule's time-stop multiplier and RSI-overbought threshold (default 2x/70, matching the validated rule) — added specifically for the handoff doc's one-shot "relax the exit and re-test once, no iterating" experiment; don't treat repeated use of these flags as license to keep tuning past that one attempt.

Default universe/lookback are wide by design (a first narrower run undershot the 30-trade minimum): `--crypto` omitted means all `get_all_krw_markets()[:80]` (same range as live `scan_crypto`) at `--crypto-count` candles (default 5000 — `get_krw_candles`'s pagination just stops early once a market's listing history runs out, so this isn't a hard requirement); `--krx` omitted means `KRX_MARKET_CAP_TOP`, a static large-cap KOSPI/KOSDAQ snapshot pending real market-cap-ranked scanning once Toss API integration lands (delisted/merged codes in it just get skipped). `--count` (KRX/US-stock lookback) defaults to 1500. Both `--crypto` and `--krx` still accept explicit values to narrow scope for a quick run.

**`index.html`** — static single-page dashboard (Chart.js via CDN) that fetches `portfolio.json` and `last_report.json` directly (cache-busted) and renders cash/positions/pending approvals/conviction holdings. It has no build step; it's served as-is (e.g. GitHub Pages) and only reads JSON, never writes it — approve/reject from the dashboard just copies the `/approve <id>` / `/reject <id>` command to the clipboard for the user to paste into Telegram.

**`real_portfolio_sync.py`** — read-only real-account bridge (PR#7/#8, merged 2026-08-01), run manually via `sync_real.yml`. **`on: workflow_dispatch:` only — no `schedule:` block, so this never runs on its own; it only fires when someone explicitly dispatches it.** Calls Toss Securities' official Open API through a fixed-egress-IP proxy (`PROXY_URL`, IP-whitelisted by Toss): OAuth2 client-credentials token (`POST /oauth2/token`), then account list → holdings → buying-power → exchange-rate (all `GET`), normalizes the result, and writes it to `real_portfolio.json` — a file kept deliberately separate from the simulation's `portfolio.json` so the two code paths never cross. **Code-level audit (2026-08-01): every HTTP call in the file is enumerated above — one `POST` (auth token) and the rest `GET`; there is no endpoint, function, or code path resembling placing/submitting/executing an order anywhere in the file.** `sync_portfolio()` only reads.

**"조회" (read) and "주문 실행" (order execution) are two different things — don't conflate them when judging whether Track B is active.** Track B (real-money auto-trading) requires *both* of the following to be true at once: (1) order-execution code exists somewhere in the codebase (a function that actually places/submits/cancels an order against a broker API — `real_portfolio_sync.py` has none), *and* (2) something triggers it automatically without a human in the loop (a `schedule:` cron, not `workflow_dispatch:`). Merging a read-only account-balance sync, even one that's fully implemented and working, satisfies neither condition — it doesn't move the real account any closer to auto-trading by itself. Don't describe `real_portfolio_sync.py` as "inert"/"a stub" once it's actually implemented (it isn't inert — it does real reads against the real account), but also don't describe it as a step toward Track B without both criteria above being separately, explicitly true.

## State files (all in repo root, treated as a database)

- `portfolio.json` — `cash` + `positions[]` (market, asset_class, strategy_type, entry_price/date, amount_krw, conviction flag). Simulation only, never written to by the real-account path.
- `trade_history.json` — closed trades log (`trades[]`).
- `pending_actions.json` — actions awaiting Telegram approval (`actions[]`, status: `waiting`/`approved`/`rejected`). Virtual-portfolio entries use `type: sell|buy` + `market`/`reasoning`. Real-account entries (`TRACK_B_ENABLED` suggestion gate, added 2026-08-01) use a deliberately separate field set instead of overloading `type` — `action_type: sell|rebalance`, `target_account: "real"`, `market` (bare symbol, e.g. `"005930"`), `name`, `dry_run: true|false` — so `check_updates.py` can dispatch on `target_account` before ever touching the virtual-portfolio-mutating code that assumes `type`.
- `real_portfolio.json` — real Toss account snapshot (2026-08-01), written by `real_portfolio_sync.py`/`sync_real.yml`. `synced_at`, `cash` (KRW total, USD folded in via the live exchange rate), `positions[]` (`symbol`/`name`/`market_country`/`currency`/`quantity`/`avg_price`/`current_price`/`eval_amount`/`eval_amount_krw`/`return_pct`). **Deliberately excludes `accountNo`/`accountSeq`** — those exist only in-memory in `real_portfolio_sync.py` to build the `X-Tossinvest-Account` header and are never logged or persisted, since this repo is public. Read (not written) by `analyze.py` for the `TRACK_B_ENABLED` suggestion gate above.
- `last_report.json` — denormalized snapshot for `index.html`; kept in sync by both `analyze.py` and `check_updates.py`.
- `telegram_offset.json` — last processed Telegram `update_id`, owned by `check_updates.py`.

Both GitHub Actions workflows commit these files back to the branch after running (`git add ...; git commit; git push`), so the two workflows (`daily.yml` at 11:00 UTC, `poll.yml` every 15 min) can race on the same files — be aware of that when changing commit/push logic or file schemas, since a schema change must stay compatible with whatever the other workflow's last commit wrote.

`backtest_report.json` (repo root, written by `backtest.py`/`backtest.yml`) is a separate output, not part of the daily/poll state and not read by `index.html` — it doesn't participate in the race above.

## Conventions specific to this repo

- User-facing strings (Telegram messages, report text, dashboard labels) and strategy-type values (`단타`/`스윙`/`장기`, `매수`/`매도`/`보유`/`비중조정`) are in Korean — keep new user-facing text and the JSON `action`/`strategy_type` vocabulary consistent with the existing Korean terms rather than switching to English.
- Claude is prompted to return *only* raw JSON; `ask_claude_decision` defensively strips code fences and extracts the outermost `{...}` before parsing, and retries once on failure. Preserve this defensiveness if you touch the prompt or parsing.
- Failures in price lookups, news fetches, or AI calls are caught and degrade gracefully (falling back to entry price, "뉴스 조회 실패", or an error message sent to Telegram) rather than crashing the workflow — the daily/poll Actions must keep running and committing state even when an external API is down.

## Working principles

- When you modify code, briefly explain *why* you changed it that way, not just what changed.
- Never remove or weaken the safety guardrails (hard stop-loss thresholds, the approval requirements for long-term/stock/large-position trades) as a side effect of an unrelated change. If a guardrail genuinely needs to change, call it out explicitly and confirm with the user first.
- Don't take this simulation toward real-money execution on your own initiative — that transition is a deliberate, separately-discussed decision gated on backtest results.
- **While the backtest gate (계획서 v3.1 §2.1) has not passed, do not add or re-enable a real-time external data connector (news APIs and similar — this explicitly includes anything in the `get_news_headlines` family) on your own judgment within a session.** Get sign-off in a direction-setting session (claude.ai) first, then connect it. This was written after `get_news_headlines` got wired into `ask_claude_decision`'s live approval flow without validation and had to be reverted same-day (PR#4) — see the Phase 2 news-events paragraph above.
