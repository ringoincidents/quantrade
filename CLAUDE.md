## ⚠️ v3.2 전환 (2026-08-03) — 예측은 비활성, AI 역할이 바뀌었다

**이 문서를 읽는 세션은 이 절을 먼저 읽어라.** 아래 나머지 서술 상당수는 v3.1 시절(예측이 활성이던 때)에 쓰였고, 그 시절 동작을 설명하는 대목은 *역사적 기록*으로 남겨둔 것이지 현재 동작이 아니다.

**무엇이 바뀌었나**: 계획서 v3.1은 AI에게 **알파 생성**(BUY/SELL 방향 판단)을 맡겼다. 두 신호원이 모두 §2.1 게이트를 통과하지 못해 그 역할을 거둔다.

- **가격 신호** (`entry_score` → MA/ADX/RSI 계열, 백테스트 583~706건 규모): 게이트 미통과.
- **뉴스 방향 판단** (`ask_news_event_judgment`, 과거 뉴스 706건): 게이트 미통과. 그뿐 아니라 **단순 다수클래스 baseline보다도 적중률이 낮았다** — 고확신군조차 세 window 전부 baseline 미달(D+1 −8.82p / D+5 −3.04p / D+20 −5.53p)이었고, 방향별 적중률이 기저비율과 사실상 동일(D+1 호재 40.0% vs 기저 40.1%)해 방향 판단에 정보가 없다는 결론이 나왔다. 근거: `Phase2_과거뉴스백테스트_설계.md` §8.

**예측(BUY/SELL 방향 판단)은 현재 비활성이다. 이것은 두 신호원의 실패에 따른 결정이며, 영구 포기가 아니라 보류다.** 재개하려면 **다시 §2.1 게이트를 통과해야 한다** — "이번엔 될 것 같다"거나 프롬프트를 고쳤다는 이유로 재활성화하지 않는다. 관련 코드·데이터·로그는 전부 보존돼 있다(삭제 금지, 아래 참조).

**v3.2에서 AI가 맡는 역할은 두 가지뿐이다:**

**(a) 리스크 가드레일 — 규칙 기반, 결정론적.** 하드 손절, 비중 상한, 현금 비율 같은 *사전에 정해진 규칙*의 위반 여부만 판정한다. AI의 판단이 개입하지 않으므로 **통계 게이트(§2.1) 적용 대상이 아니다** — 예측이 아니라 산술이기 때문이다. 이 구분을 흐리지 마라: 규칙 위반 여부에 확신도나 승률을 붙이려는 시도가 나오면 그건 예측이 되돌아온 것이다.

**(b) 뉴스 사건 설명 카드 — 예측이 아님.** "오늘 이 종목에 이런 뉴스가 있었다"는 *사실 설명*만 만든다. **`BUY`/`SELL`/`confidence` 필드가 아예 없다** — 스키마 수준에서 없앴다. 종목별 매매 제안이나 방향 판단을 넣지 않는다.

**새 성공 지표**: "위험 행동 발견율"이 아니라 **"경고 후 실제 행동 변화 추적"**이다. 예: 과도쏠림 경고가 뜬 뒤 사용자가 실제로 포지션을 조정했는지를 로그로 남긴다. **이 지표는 통계 검정 대상이 아니다** — 표본이 작고, 사용자 1인의 행동이며, p값을 붙일 성질의 것이 아니다. 승률·유의성 검정을 이 지표에 적용하려 하지 마라(그렇게 하는 순간 예측 프레임으로 되돌아간다).

### 규칙 기반 포지션 관리 자동실행 — 방향성 세션 2026-08-04 정식 승인

**결정문(원문 그대로 기록)**: "방향성 세션 2026-08-04 정식승인, dry-run 생략 사유: 사용자 명시적 결정, 보강 안전장치로 상쇄"

**2026-08-04 2차 결정(1차 결정을 대체) — 즉시자동실행 폐기, 승인게이트로 확정.** 1차 결정 직후 같은 날 안에 실행 방식이 다시 바뀌었다: "규칙 발동 → 즉시 자동실행 → 사후 텔레그램 통보"였던 것을 **"규칙 발동 → 심층분석 리포트 생성 → 텔레그램으로 리포트+승인요청 전송 → 사용자가 `/autoexec_approve`한 뒤에만 실행"**으로 바꿨다(`autoexec.py`의 `REQUIRE_APPROVAL = True`, `rule_trigger_report.py`가 리포트 생성기). 규칙 발동 감지(집중도/손실지속/목표가 세 규칙의 산술)와 1일 1회 제한·30% 매도 상한 같은 기존 안전장치는 이 변경과 무관하게 그대로다 — 바뀐 건 "발동 후 무엇을 하는가"뿐이다. **1차 결정의 "dry-run 생략" 관련 보강 안전장치(사후 통보·전량 로깅·킬스위치·레이트리밋)는 승인게이트가 생기면서 최종 방어선으로서의 중요도는 낮아졌으나(이제 실행 전에 사람이 리포트를 보고 결정하므로) 계속 유지한다** — 승인 이후에도 킬스위치는 여전히 실행을 막을 수 있어야 하고(`handle_autoexec_approve`가 승인 시점에도 킬스위치를 재확인한다), 전량 로깅은 승인/거절/만료 판단의 근거로 계속 쓰인다. 토스 주문 API 스펙 부재로 3단계(실주문)가 막혀 있다는 사실은 이 변경으로 달라지지 않는다 — 이번 변경은 "승인 없이 실행하지 않는다"는 실행 방식만 바꾼 것이지, 애초에 실행 계층 자체가 없다는 블로커를 푼 게 아니다.

`RULE_BASED_AUTOEXEC_ENABLED`(`analyze_lib.py`, 기본 `false`)가 이 기능의 마스터 스위치다. **`TRACK_B_ENABLED`와는 별개의 플래그이며 코드 상 두 플래그 사이에 어떤 참조 관계도 없다** — 서로의 조건문에 등장하지 않고, 한쪽이 다른 쪽을 읽거나 바꾸지 않는다(`TRACK_B_ENABLED`는 여전히 정의되지 않은 예약 이름이다).

- **매도/리밸런싱 전용.** `autoexec.py`의 `execute()`는 `sell` 이외의 action을 예외로 거부하고, 매수 후보를 만드는 함수가 파일에 존재하지 않는다. self-test가 모듈 네임스페이스에 매수 관련 호출 가능 심볼이 없음을 검사한다.
- **세 규칙**: 집중도 리밸런싱(비중 >30%, 1회 매도 상한은 해당 종목 평가액의 30%) / 손실 지속 손절(-50% 이하 60일 지속, 세금손실 활용 문구 포함) / 목표가 부분익절(`target_prices.json`).
- **목표가는 사람이 수기 입력한 값만 쓴다.** `autoexec.py`에는 Claude API 호출이 없고 self-test가 AI 관련 심볼 부재를 검사한다. 목표가를 코드가 계산·제안하는 경로를 만들지 않는다.
- **승인 게이트(2차 결정, 위 참조).** 규칙 발동 시 즉시 실행하지 않고 `queue_for_approval()`로 승인 대기(`autoexec_state.json`의 `pending_approvals`)에 올리며, 동시에 `rule_trigger_report.generate()`로 심층분석 리포트를 만들어 `autoexec_reports.json`에 저장한다. 텔레그램 승인요청 메시지는 규칙명·발동사유(사실)·리포트 요약을 담고 `/autoexec_report <id>`(전체 리포트 재조회)·`/autoexec_approve <id>`·`/autoexec_reject <id>` 안내를 포함한다(`check_updates.py`). 같은 날 같은 규칙·종목 중복 등록 방지, `APPROVAL_TTL_DAYS`(2일) 경과 시 만료. 리포트는 BUY/SELL·confidence·목표주가 같은 예측성 필드/문구를 금지어 감사(`rule_trigger_report.audit()`)로 걸러낸다 — 승인 근거가 예측으로 오염되지 않게 하기 위함이다.
- **안전장치**: 킬스위치(`/autoexec_stop`, 해제는 `/autoexec_start`로만 — 재시작으로 풀리지 않음; 규칙 발동→승인대기 등록 이전과 `/autoexec_approve` 실행 시점 양쪽에서 확인해 승인요청 전송 자체와 실행 둘 다 차단한다), 발동·미발동 전량 로깅(`autoexec_log.json`), 승인 게이트(위 항목 — 실행 즉시 사후 통보가 아니라 사전 승인), 첫 7일 규칙별 1일 1회 제한.
- **활성화 순서(건너뛰지 말 것)**: 킬스위치 테스트 → 안전장치 전부 검증 → 그 다음에만 플래그 `true`.

**2026-08-08 상태 미영속화 버그 발견 및 수정.** 킬스위치 테스트(위 활성화 순서의 1단계) 중 `/autoexec_stop`/`/autoexec_status`에 봇이 응답하지 않는 문제를 조사하다 발견: `poll.yml`/`daily.yml`의 "Commit state" 스텝이 `autoexec_state.json`을 커밋 대상에 넣지 않고 있었다. `check_updates.py`의 `handle_autoexec_stop()` 등은 CI 잡 안에서 이 파일을 정상적으로 썼지만, `git add` 목록에 없어 그 변경은 잡이 끝나는 순간 사라졌다 — **텔레그램 회신("🛑 자동실행 킬스위치 작동")은 정상으로 갔지만 실제로는 한 번도 저장소에 영속된 적이 없었다**(전체 git 히스토리 확인 결과 `autoexec_state.json`이 커밋된 적 자체가 없었음). `RULE_BASED_AUTOEXEC_ENABLED`가 계속 기본값 `false`였고 `autoexec.run()`을 스케줄로 도는 워크플로 자체가 없어(`daily.yml`은 `analyze.py`만 실행, `autoexec.yml`은 존재하지 않음 — 그래서 세 규칙의 실제 판정도 지금까지 스케줄로 돈 적이 없다) 이 버그가 실거래에 영향을 준 적은 없지만, 플래그를 켜기 전에 반드시 통과해야 하는 "킬스위치 테스트" 단계가 실제로 그 역할을 했다는 사례로 남긴다. 수정: `poll.yml`의 커밋 스텝에 `autoexec_state.json`/`autoexec_log.json`/`autoexec_reports.json` 추가(파일이 없을 수 있는 두 개는 개별 존재 확인 후 add — 없는 경로에 `git add`하면 `bash -e`라서 스텝 전체가 실패한다).

**2026-08-08 킬스위치 반영 지연 — 별개 사실, GitHub 플랫폼 한계.** `poll.yml`의 cron 선언(`*/15 * * * *`)과 실제 실행 간격을 비교했더니 40~90분 차이가 관측됐다 — GitHub Actions의 `schedule` 트리거가 플랫폼 부하 시(특히 매 시 정각 전후) 지연될 수 있다고 공식 문서에 명시된 한계이며, 워크플로 설정만으로는 없앨 수 없다. 대응: (1) `poll.yml`을 GitHub의 실질 최소 간격인 `*/5`로 단축. (2) `/autoexec_stop` 전용 별도 워크플로 `autoexec_stop_fast.yml`(`autoexec_stop_fast.py`) 추가 — 같은 5분 간격이지만 목적은 "더 자주 도는 것"이 아니라 GitHub의 스케줄 지연이 `poll.yml` 한쪽에만 몰릴 확률을 낮추는 이중화다. 이 스크립트는 `telegram_offset.json`을 **절대 전진시키지 않는다** — `poll.yml`이 마지막으로 확정한 값을 읽기만 해서 같은 값으로 `getUpdates`를 조회하므로, 두 워크플로가 같은 텔레그램 업데이트 큐를 두고 경쟁해 서로 못 보게 만드는 일이 없다. `/autoexec_stop`을 발견하면 킬스위치만 즉시 걸고(`autoexec_state.json`만 커밋 — `telegram_offset.json`은 손대지 않음) 짧은 확인 메시지를 보낸다; 중복확인 회신·오프셋 전진 등 "정식 처리"는 여전히 `poll.yml`의 정규 주기가 맡는다(그래서 같은 정지 명령에 알림이 두 번 갈 수 있다 — 의도된 중복, `engage_kill_switch`는 멱등). `/autoexec_start`(재개)는 이 빠른 경로에 넣지 않았다 — 안전 기본값은 "정지된 쪽"이라 재개가 늦는 것보다 정지가 늦는 게 더 위험하다는 판단. **웹훅(텔레그램이 즉시 push) 전환은 근본적으로 이 지연을 없애지만 상시 대기 서버가 필요해 "GitHub Actions가 유일한 런타임, 서버 없음"이라는 이 저장소의 설계 원칙과 정면으로 부딪힌다** — 별도 인프라 결정으로 보류했고 이 세션에서 구현하지 않았다. **위 두 수정 이후에도 남는 사실**: 두 경로 모두 `schedule:` 트리거를 쓰는 한 "즉시"를 보장하지 않는다(5분 간격 자체 + 플랫폼 부하 시 추가 지연 가능) — `RULE_BASED_AUTOEXEC_ENABLED` 전환 여부를 논의하는 방향성 세션은 이 지연 특성을 감안해야 한다. 대시보드(`index.html`, "🛑 킬스위치 상태" 블록)에도 이 사실을 노출한다.

**2026-08-08 GitHub Actions 스케줄 신뢰성 자체가 이슈로 확인됨 — 실거래 자동화 전 재검토 필요.** 실사용자 텔레그램 로그로 킬스위치 응답 시각을 재검증하던 중, `poll.yml`이 예약 실행이든 수동 실행이든 **72분간 단 한 번도 실행되지 않은 구간**이 실제로 관측됐다(11:31:43~12:44:03 KST, GitHub Actions 실행 이력 자체에 해당 구간 항목이 없음 — 돌았는데 응답을 못 보낸 게 아니라 잡이 아예 시작되지 않음). 이 사건은 상태 미영속화 버그 수정(PR#15, 14:42:59 KST 병합) **이전**에 일어났으므로 수정본이 실패한 사례는 아니지만, `poll.yml`/`autoexec_stop_fast.yml`을 5분 간격으로 단축한 뒤에도 신설 워크플로 `autoexec_stop_fast.yml`이 병합 후 22분간 실행 이력 0건인 구간이 별도로 관측됐다(`킬스위치_타이밍조사_2026-08-08.md` 참고, 자세한 시각표와 실행 로그 원문 포함). 원인은 GitHub Actions 플랫폼 레벨 지연으로 추정되며 코드 문제가 아니다 — 실제로 잡이 시작되기만 하면 처리·응답까지 8초가 걸리지 않았다(§ 위 킬스위치 반영 지연 항목 참고). 이 세션에서 직접 GitHub 공식 문서(`docs.github.com`)를 열지는 못했지만(정책 차단, `토스_주문API_스펙조사_2026-08-05.md`와 같은 유형의 제약), 검색으로 확인한 문서 요지("scheduled workflows can be delayed during periods of high load, especially the start of every hour")와 GitHub 스태프가 공개 커뮤니티 스레드에서 직접 인정한 발언("the drift on the start of our scheduled jobs has got worse... scheduled drops have grown >30% in 2ish months", `github.com/orgs/community/discussions/156282`)이 이 현상과 일치한다 — 1급 소스로 재확인은 못 했으나 복수의 정황 증거가 같은 방향을 가리킨다. **킬스위치를 `schedule:` 기반 워크플로에만 의존시키는 현재 설계는 실거래 자동화(RULE_BASED_AUTOEXEC_ENABLED 전환) 전에 재검토가 필요하다 — 방향성 세션 안건으로 남긴다.** 대안으로 `workflow_dispatch`(수동 트리거)를 킬스위치 보조 경로로 병행하는 방안을 조사만 했다(구현 안 함): 이번 조사 세션이 실제로 여러 차례 강제 트리거를 사용했는데, 매번 대기열 등록부터 실행 시작까지 몇 초~수십 초 내로 시작됐다 — `schedule:` 이벤트가 겪는 것과 같은 배치 지연 큐를 타지 않는 것으로 보인다(1급 소스 확인은 아니고 이번 세션의 반복 관측). 다만 `workflow_dispatch`는 사람(또는 GitHub 저장소 쓰기 권한이 있는 세션)이 직접 눌러야 하는 수동 경로이며, "예약 실행이 안 됐으면 자동으로 수동 트리거"처럼 스스로 감시하는 자동 백업을 만들려면 결국 GitHub Actions 바깥의 무언가(웹훅과 같은 종류의 상시 대기 인프라)가 필요해 위 웹훅 논의와 같은 "서버 없음" 설계 원칙 충돌로 되돌아간다 — 그래서 이번엔 가능성만 기록하고 아무것도 만들지 않았다.

**주문 실행 계층에 대한 사실**: 이 저장소에는 여전히 주문을 넣는 코드가 없다. 2026-08-08 확인 — 토스증권 Open API에 주문 생성·정정·취소와 조건주문(SINGLE/OCO/OTO, LIMIT/MARKET)이 **존재하며**, 인증은 기존 OAuth2 토큰 + `X-Tossinvest-Account` 헤더와 동일하다. 다만 **엔드포인트 경로와 요청 본문 필드명은 아직 확보되지 않았고**(문서 호스트가 이 환경에서 정책 차단), 그래서 `autoexec.place_sell_order()`는 미구현 상태로 호출되면 `OrderLayerUnavailable`을 던져 "실행 불가"로 로깅된다. 필드명을 추측해 넣지 않는다 — 조용히 거부되거나 다른 뜻으로 해석된 주문이 실계좌에 나갈 수 있다. 따라서 **플래그를 `true`로 바꿔도 현재는 주문이 나가지 않는다.** 이 상태가 Track B 기준과 어떤 관계인지에 대한 판정은 방향성 세션 몫이며 여기에 적지 않는다(세션 시작 체크리스트 "사실을 적고 판정을 내리지 말 것").

**dry-run 생략에 대해 코드 세션이 남기는 사실**: 사후 통보·로깅·킬스위치·레이트리밋은 *잘못된 실행이 일어난 뒤의* 피해를 줄이거나 반복을 막는 장치다. *수량·종목을 잘못 계산하는 버그 자체*를 실행 전에 잡아내는 장치는 아니다. 실제로 이번 구현에서 토스 API가 `quantity`/`current_price`를 문자열로 준다는 사실 때문에 수량 계산이 실계좌 데이터에서 크래시했고, self-test는 정수 픽스처를 쓰고 있어 통과하고 있었다(문자열 픽스처 회귀 테스트를 추가해 막았다). 이 사실을 기록해 두는 것이 판단을 뒤집자는 뜻은 아니며, 결정은 위 결정문대로 유효하다.

**보존 원칙**: 기각된 신호 로직(`entry_score`, `scan_crypto`/`scan_stocks`, `ask_claude_decision`의 예측 경로, `backtest.py`, 뉴스 방향 판단 트랙)은 **삭제하지 않는다.** 실행 경로만 끊고 "기각된 연구 결과, 활성 기능 제외" 표시를 달아 남긴다 — 나중에 왜 기각됐는지 재구성할 수 있어야 하고, 재개 시 게이트를 다시 돌릴 대상이기도 하다.

## What this is

**(아래 문단은 v3.1 시절 서술이다. "asks Claude for buy/sell/hold decisions"와 "executes trades"는 v3.2에서 비활성 — 위 전환 절 참조.)**

Quantrade is a personal quant portfolio bot ("분석, 추후엔 자동 거래" — analysis now, autotrading later). It scans Korean crypto (Upbit) and US stocks, asks Claude for buy/sell/hold decisions, executes small/low-risk trades automatically, and queues larger or riskier trades for manual approval via Telegram. State lives entirely in JSON files committed to the repo; GitHub Actions is the runtime (there is no server).

There are no tests, no linter config, and no dependency manifest (`requirements.txt`) in this repo — the only third-party dependency is `requests`, installed inline in CI (`pip install requests`). When changing code, mirror that: keep dependencies minimal and don't introduce a build/test toolchain unless asked.

## Project context

- This is a personal AI investment-decision *assistant*, not an autotrader — every non-trivial trade is either auto-executed under tightly bounded safety rules or held for explicit human approval via Telegram. Do not blur that line.
- The user is doing mandatory military service and only has PC access ~6-9am at a "cyber knowledge information room" (사이버지식정보방); the rest of the time they interact via the mobile Claude app. Code changes now happen through Claude Code. Keep this in mind for anything time-sensitive (e.g. don't assume same-day follow-up is possible outside that window).
- The project is in a validation/trial phase running through December 2026 — this is a virtual simulation with no real trades yet. Expanding to real trading is only to be discussed after backtest validation, not implemented unprompted.
- Asset coverage is actively transitioning from crypto (Upbit) to domestic Korean stocks via the Toss Securities API, because crypto exchange sites are blocked on the military network. Expect `analyze_lib.py`'s crypto-scanning code to be gradually replaced/supplemented by Toss-based stock scanning — when working here, check whether the crypto path is still the active one or already superseded.
- Overall project direction/roadmap lives in a separate planning document outside this repo; ask the user for it if you need it rather than assuming.

## Architecture

**`analyze_lib.py`** — all shared logic and I/O: technical indicators (MA, RSI, Bollinger bands), Upbit/Yahoo/stooq/Naver market data fetchers (including `get_krx_candles`, a Naver-based historical fetcher for Korean stocks used until the Toss Securities API is wired in), the shared entry-scoring rule (`entry_score`, used by both live scanning and the backtest engine so they can't drift apart), crypto/stock candidate scanning (`scan_crypto`, `scan_stocks`), Google News RSS sentiment scoring (`get_news_sentiment`), the Claude API call that turns holdings + candidates + news into a decision JSON (`ask_claude_decision`), Telegram sending, and generic `load_json`/`save_json` helpers. Constants here (`HARD_STOP_LOSS`, `EXCLUDE_MARKETS`, `US_STOCKS`, `TRADING_COSTS`, sentiment word lists, `AI_SUGGESTION_DRY_RUN`) are the tunable knobs for strategy behavior. `ask_claude_decision` takes an optional `real_positions` list (symbol/name/quantity/current_price/return_pct only — never account numbers) and instructs Claude to prefix any real-account decision's `market` field with `REAL:` so `analyze.py` can route it without colliding with virtual-portfolio market strings of the same ticker (e.g. `NVDA` exists in both `US_STOCKS` and the user's real holdings).

**Phase 2 news-events work exists but is deliberately *not* wired into the live decision flow.** `entry_score` (RSI + Bollinger) still gates which candidates `scan_crypto`/`scan_stocks` surface each day — kept for practical reasons (the full ~80-market crypto universe can't all be sent to Claude daily) — and its docstring now frames it as a pre-filter rather than a trading thesis, but `ask_claude_decision` itself still runs on the original `get_news_sentiment` keyword-count + unmodified prompt, exactly as before Phase 1's gate failed. A same-day attempt to replace `get_news_sentiment` with `get_news_headlines` (raw headline text passed straight into the prompt, with an explicit "price metrics aren't the basis, news events are" instruction) was built and merged, then **reverted** within hours: shipping an unvalidated prompt/judgment change straight into the real approval flow (even with Track B disabled, this still drives what a human sees and acts on via Telegram) violated the "safety nets and approval criteria don't change before validation" principle. `get_news_headlines`/`_format_news` are kept in the file (not deleted) as a standalone, disconnected utility for future experiment scripts — event-type classification (실적발표/공시/M&A/규제) and the KRX-only scope for that work are still to be designed, and reconnecting it to `ask_claude_decision` is an explicit separate decision gated on calibration results, not something to do inline. `HARD_STOP_LOSS` was never touched by any of this — it's the one AI-independent, unconditional safety net the eventual news-driven design is modeled after.

`get_us_closes` tries Yahoo Finance's chart API first, then falls back to stooq — stooq alone was confirmed (during the phase-1 backtest run) to return a bot-detection challenge page instead of CSV from GitHub Actions IPs, which meant `scan_stocks` had likely been silently finding zero US stock candidates in every daily run (no `asset_class: "stock"` entries ever appear in `portfolio.json`/`trade_history.json`). This edit could not be network-tested in the editing sandbox (all outbound hosts were proxy-blocked there) — confirm it actually works by checking `daily.yml`/`backtest.yml` logs after this lands, and add another fallback if Yahoo also turns out to be blocked from Actions IPs.

**`analyze.py`** — the daily cycle (`run()`), driven by `daily.yml`:
1. Price every held position, compute return %.
2. Scan for new crypto/stock candidates, classify each by expected holding period into a strategy: 단타 (day, ≤6 days), 스윙 (swing, ≤20 days), 장기 (long-term, >20 days) — see `classify_strategy`/`estimate_holding_period`.
3. Send all holdings + candidates + news to Claude (`ask_claude_decision`) for a market summary and per-market decisions.
4. Apply decisions:
   - Hard stop-loss (`HARD_STOP_LOSS` per strategy type) always fires immediately regardless of AI decision.
   - Otherwise, a sell/buy either executes automatically or goes into `pending_actions.json` awaiting Telegram approval, based on `needs_approval()`: 장기 (long-term) positions, `stock`/`krx` asset classes, or positions ≥10% of total assets (`AUTO_TIER_WEIGHT`, `analyze_lib.py`) all require approval; small crypto swing/day trades below that weight execute automatically.
   - **Position sizing / Risk Engine (2026-08-01 design, simulation-only):** two constants in `analyze_lib.py` — `AUTO_TIER_WEIGHT = 0.10` (auto-execute ceiling; a candidate sized at or above 10% of total assets routes to approval instead) and `POSITION_WEIGHT_HARD_CAP = 0.20` (absolute per-position ceiling — even a Telegram-approved buy is clamped down to 20% of total assets if the AI-suggested weight exceeds it, with a warning line in the report). `MIN_CASH_RESERVE_RATIO` (in `analyze.py`) was raised 0.2 → 0.3, i.e. total risk-asset exposure is capped at 70% instead of 80%, in response to the Phase 1 backtest gate not passing. Fixed alongside this: `min_cash` is now computed as `total_assets * MIN_CASH_RESERVE_RATIO` (live current total assets), not the old fixed `TOTAL_BUDGET` — previously the cash reserve didn't grow or shrink with the portfolio's actual size, which defeated the point of a *ratio*. **This entire mechanism (`needs_approval()`, the auto-tier, the hard cap) only ever touches `portfolio.json`, the simulation state `analyze.py`/`check_updates.py` read and write.** `real_portfolio_sync.py` (see below) now does real, working **read-only** account syncs (PR#7/#8) — a factual update from this constant's original 2026-08-01 design note, which described it as a `NotImplementedError` stub; it no longer is. Real-account sell/rebalance suggestions (`AI_SUGGESTION_DRY_RUN`, see below) never go through `needs_approval()`/the auto-tier at all and always require approval unconditionally — and that gate is a distinct, narrower mechanism than "Track B" as strictly defined further down (order-execution code + an automatic trigger, neither of which exist); flipping `AI_SUGGESTION_DRY_RUN` alone doesn't satisfy either criterion.
   - The `conviction: true` flag has no interaction with any of the above — it's only ever set post-buy via the `/keep` Telegram command, and is only checked in the sell-decision loop (to skip automated sell/hold for pinned positions). It cannot be used to route a buy around `AUTO_TIER_WEIGHT`/`POSITION_WEIGHT_HARD_CAP`, since those checks happen at buy time, before any position (and thus any conviction flag) exists.
5. Persist `portfolio.json`, `trade_history.json`, `pending_actions.json`, and a dashboard-facing snapshot `last_report.json`, then send the report text to Telegram.

**Real-account suggestion dry-run gate (`AI_SUGGESTION_DRY_RUN`, 2026-08-01, renamed 2026-08-02) — a different, narrower mechanism than "Track B" below, not an alternate name for it.** "Track B" (further down) is strictly defined as real-money *auto-trading*: order-execution code plus an automatic trigger, both currently absent. `AI_SUGGESTION_DRY_RUN` only controls whether AI-generated **suggestions** on real holdings are labeled dry-run — nothing it gates ever places an order, and it never moves either Track B criterion to true. This flag was originally named `TRACK_B_ENABLED`; that name is now **reserved** for the actual future "order-execution + auto-trigger" master switch described in the Track B section below — do not reuse it for anything else, and do not create that switch preemptively (there's no order-execution code yet for it to gate). `real_portfolio_sync.py` is a working read-only sync against the official Toss Open API (OAuth2 client_credentials → `GET /api/v1/accounts` → `/holdings` → `/buying-power` → `/exchange-rate`, hardcoded to the confirmed spec since it's no longer unverified), run manually via `sync_real.yml` (`workflow_dispatch`, commits `real_portfolio.json`). `analyze.py` loads `real_portfolio.json` and passes a stripped-down view (symbol/name/quantity/current_price/return_pct — **never `accountNo`/`accountSeq`**, checked into `real_portfolio.json` in the first place: see State files below) into `ask_claude_decision`, which can propose `REAL:`-prefixed sell/비중조정 decisions for real holdings. `analyze.py` routes any such decision straight into `pending_actions.json` with `target_account: "real"` — **it never runs through `needs_approval()`/the auto-tier; every real-account suggestion requires Telegram approval, unconditionally, with no exceptions.**
- `AI_SUGGESTION_DRY_RUN` (env var, `analyze_lib.py`, default `"true"`) is this gate — note the flag itself is dry-run-positive, the inverse polarity of the old `TRACK_B_ENABLED`. While it's `true` (the only state so far), every real-account `pending_actions` entry is written with `"dry_run": true` and its Telegram/report text carries an explicit `[모의]` (mock) tag. `check_updates.py`'s `handle_approve` special-cases `target_account == "real"` **before** the normal sell/buy dispatch: it replies that the gate hasn't passed and does **not** change the action's status (`/approve` is a safe, repeatable no-op) — `/reject` still works normally (dismissing a suggestion is never unsafe).
- **Even with `AI_SUGGESTION_DRY_RUN=false`, nothing executes** — there is no order-placing code anywhere in this repo for the real account (`real_portfolio_sync.py` is deliberately read-only), so `handle_approve` on a non-dry-run real-account action currently just replies that execution isn't implemented. The flag exists so that decision can be made independently of (and after) building actual order execution, not as a stand-in for it — and even once it's off, that still isn't Track B (see above).
- **`AI_SUGGESTION_DRY_RUN` must stay `true` until an explicit gate-passed decision** (per the 2026-08-01 handoff doc, expected around end of October 2026, decided in a claude.ai direction-setting session — not something to flip inline while doing unrelated work). Flipping it currently only removes the `[모의]` label and sets `dry_run: false` in new pending actions; it has no execution effect today, but treat it as a guardrail anyway, per the "confirm before changing safety nets" principle below. **Turning it to `false` requires sign-off in a direction-setting session (claude.ai) first — do not flip it based on a same-session judgment call, no matter how well-guarded the change looks.**
- **Real-account data has two different, separately-scoped uses — don't let approval for one imply approval for the other.** Showing `real_portfolio.json` on the dashboard (a human looks at it) is an already-approved use. Feeding it into `ask_claude_decision` so Claude generates suggestions is a *different* use, and is only approved in the `dry_run` state — actually using those suggestions (`AI_SUGGESTION_DRY_RUN=false`) is not approved and needs the same direction-setting sign-off as above.

**`check_updates.py`** — the Telegram command loop (`run()`), driven by `poll.yml` every 5 min (2026-08-08, down from 15 min — see the autoexec section above for why: GitHub's `schedule` trigger doesn't guarantee the declared interval, and this is the platform's practical floor, not a fix for that). Long-polls `getUpdates` since `telegram_offset.json`'s last update id, and handles:
- `/approve <id>` / `/reject <id>` — resolve a pending action from `pending_actions.json`. `handle_approve`/`handle_reject` both branch on `target_account == "real"` first (the `AI_SUGGESTION_DRY_RUN` suggestion gate, see above) before falling through to the normal virtual sell/buy dispatch — a real-account action never reaches the `portfolio.json`-mutating code path.
- `/keep <market>` / `/unkeep <market>` — toggle the `conviction` flag on a held position.
- `/status` — report current positions back to Telegram.

After any state change it also refreshes `last_report.json` (`refresh_last_report`) so the web dashboard reflects approvals immediately rather than waiting for the next daily run.

**`backtest.py`** — Phase 1 backtest engine (계획서 v3 §5), run manually (CLI or `backtest.yml` workflow_dispatch), separate from the daily/poll cycle. **Its entry signal is intentionally decoupled from live scanning** (`scan_crypto`/`scan_stocks`/`entry_score` in `analyze_lib.py` are untouched): after the first RSI+Bollinger-only backtest failed to hold up in validation, the strategy was redesigned around trend-following — a 20/60-day moving-average golden cross gated by ADX ≥ 25 (`is_golden_cross`, `calc_adx` in `analyze_lib.py`) as the main signal, with RSI/Bollinger demoted to an entry-timing filter (skip if RSI ≥ 75 or price already above the upper band) rather than an independent trigger. Don't assume backtest changes here apply to live trading — promoting a backtested rule into `entry_score` is a deliberate, separate step per "전략 검증이 아키텍처보다 먼저다" (validate before wiring into live scanning). Since past Claude decisions can't be replayed (cost + non-determinism), sell-side is still approximated with rule-based exits (hard stop-loss, RSI overbought, a time-stop at 2x the expected holding period) — a known simplification to revisit once Phase 2's AI-confidence calibration exists. Applies `TRADING_COSTS` (fee + slippage assumptions, plus a KRX sell-only `sell_tax_pct` for 증권거래세) on entry/exit, splits trades into a 70/30 train/validation set by date, and buckets results by market regime (상승장/하락장/횡보장, from trailing 60-day return) and by strategy type. Also computes a simple buy-and-hold benchmark over the same instruments/period (`buy_hold_trades`) so the strategy's numbers can be judged against "would just holding have done better" (`benchmark_buy_hold`/`strategy_vs_buy_hold` in the report) — not just against the frozen success criteria. Buy-and-hold trades are also regime-tagged (at entry only, not day-by-day through the multi-year hold) so `by_regime_strategy`/`by_regime_buy_hold` can be compared per regime. Results are checked against the frozen success criteria from 계획서 v3 §4.3 (`SUCCESS_CRITERIA`: ≥30 trades, sharpe-like ratio) and written to `backtest_report.json`. MDD (2026-08-01, updated once the Risk Engine position-sizing design landed): `compute_metrics()`/`group_metrics()` now weight each trade's contribution to the equity curve by `POSITION_WEIGHT` (= `analyze_lib.AUTO_TIER_WEIGHT`, 10%) instead of assuming each trade reinvests 100% of assets — win rate/avg return/sharpe are untouched, only the MDD equity curve changes. This brings MDD down from the old ~-98~-100% (which assumed full-notional sequential reinvestment) to numbers roughly an order of magnitude smaller, closer to what a single 10%-sized position could actually drawdown. **This is a constant 10% scaling factor, not a portfolio-level simulation** — it does not reflect actual concurrent holdings (several positions open on the same dates), diversification/correlation effects across instruments, or the real two-tier cap mix (`AUTO_TIER_WEIGHT`=10% auto-tier vs. `POSITION_WEIGHT_HARD_CAP`=20% human-approved ceiling in `analyze.py` — every trade here is scaled by the same flat 10%, not the blend of sizes a real approval flow would produce). Treat the resulting MDD numbers as a reference-only *directional improvement* over the old unweighted figure, never as an absolute drawdown estimate to quote on their own — `MDD_CAVEAT` in `backtest.py` states this explicitly and is included in every generated report's `mdd_caveat`/`gate.mdd_reference_only` fields. Per the plan, the ≥30-trade/sharpe thresholds are fixed on purpose and shouldn't be adjusted after the fact to fit results. `evaluate_gate()` bundles the full pass/fail check from the 2026-08-01 handoff doc's §2.1 gate (≥30 trades each split, validation sharpe ≥1.0, train/validation same-sign sharpe as an overfitting check, beats buy-and-hold on both splits — MDD is reported but excluded from pass/fail per its own reference-only caveat) into `report["gate"]`. `--max-hold-multiplier`/`--rsi-exit` override the exit rule's time-stop multiplier and RSI-overbought threshold (default 2x/70, matching the validated rule) — added specifically for the handoff doc's one-shot "relax the exit and re-test once, no iterating" experiment; don't treat repeated use of these flags as license to keep tuning past that one attempt.

Default universe/lookback are wide by design (a first narrower run undershot the 30-trade minimum): `--crypto` omitted means all `get_all_krw_markets()[:80]` (same range as live `scan_crypto`) at `--crypto-count` candles (default 5000 — `get_krw_candles`'s pagination just stops early once a market's listing history runs out, so this isn't a hard requirement); `--krx` omitted means `KRX_MARKET_CAP_TOP`, a static large-cap KOSPI/KOSDAQ snapshot pending real market-cap-ranked scanning once Toss API integration lands (delisted/merged codes in it just get skipped). `--count` (KRX/US-stock lookback) defaults to 1500. Both `--crypto` and `--krx` still accept explicit values to narrow scope for a quick run.

**`index.html`** — static single-page dashboard (Chart.js via CDN), no build step, served as-is (e.g. GitHub Pages), only reads JSON and never writes it. **2026-08-02 rebuild: the old virtual-portfolio-simulation view (crypto-heavy `portfolio.json` cash/positions/pending-approvals/conviction-holdings card) was removed entirely** — Phase 1's backtest gate failed and the project's live-decision focus has moved on, so a dashboard centered on the virtual sim no longer reflected what mattered. **`real_portfolio_sync.py`** — read-only real-account bridge (PR#7/#8, merged 2026-08-01), driven by `sync_real.yml`. **As of 2026-08-02 this runs on a `schedule:` cron (`25 0,3,7,11 * * *` UTC, 4x daily) in addition to `workflow_dispatch:`** — before that it was dispatch-only. Stated plainly and without assessment: **the infrastructure for automatic, unattended real-account *reads* now exists**; what it does on each firing is unchanged (the same GETs it always made), and no order-placing code was added or exists. Whether that bears on the Track B criteria further down is a determination for a direction-setting session, not something recorded here (see that section). **The user explicitly approved this change in the 2026-08-02 session after the session flagged it and declined to proceed unilaterally** — noted here because the approval happened in a code session rather than a claude.ai direction-setting session, which is worth being able to trace later. Not fixed by re-picking a minute (a 5-min grid collides with any fixed minute eventually); the existing rebase+retry loop is what actually keeps this safe, not the minute choice. Calls Toss Securities' official Open API through a fixed-egress-IP proxy (`PROXY_URL`, IP-whitelisted by Toss): OAuth2 client-credentials token (`POST /oauth2/token`), then account list → holdings → buying-power → exchange-rate (all `GET`), normalizes the result, and writes it to `real_portfolio.json` — a file kept deliberately separate from the simulation's `portfolio.json` so the two code paths never cross. **Code-level audit (2026-08-01): every HTTP call in the file is enumerated above — one `POST` (auth token) and the rest `GET`; there is no endpoint, function, or code path resembling placing/submitting/executing an order anywhere in the file.** `sync_portfolio()` only reads.

**"조회" (read) and "주문 실행" (order execution) are two different things — don't conflate them when judging whether Track B is active.** Track B (real-money auto-trading) requires *both* of the following to be true at once: (1) order-execution code exists somewhere in the codebase (a function that actually places/submits/cancels an order against a broker API — `real_portfolio_sync.py` has none), *and* (2) something triggers it automatically without a human in the loop (a `schedule:` cron, not `workflow_dispatch:`). **Do not record a 충족/미충족 verdict against these criteria in this file.** Whether some piece of infrastructure satisfies (1) or (2) is a *determination*, and determinations about Track B belong to a claude.ai direction-setting session. A code session's job here is to state accurately what exists and leave the assessment alone — writing "criterion (2) is now true" in CLAUDE.md is itself the kind of judgment call this rule exists to keep out of code sessions. **Facts as of 2026-08-02, stated without assessment:** no order-placing/submitting/cancelling code exists anywhere in this repo; `sync_real.yml` runs a read-only account sync on a 4x-daily `schedule:` cron in addition to `workflow_dispatch:` (added 2026-08-02 with explicit user approval — see `real_portfolio_sync.py` above). A scheduled read places no orders. Don't describe `real_portfolio_sync.py` as "inert"/"a stub" once it's actually implemented (it isn't inert — it does real reads against the real account), but also don't describe it as a step toward Track B without both criteria above being separately, explicitly true. **`TRACK_B_ENABLED` is a reserved name for this eventual master switch** — it isn't defined anywhere in code yet (there's no order-execution code for it to gate); the currently-existing `AI_SUGGESTION_DRY_RUN` (see `analyze_lib.py` above) is a separate, narrower flag that only labels AI-generated real-account suggestions as dry-run and must not be confused with, or renamed back to, `TRACK_B_ENABLED`.

## State files (all in repo root, treated as a database)

- `portfolio.json` — `cash` + `positions[]` (market, asset_class, strategy_type, entry_price/date, amount_krw, conviction flag). Simulation only, never written to by the real-account path.
- `trade_history.json` — closed trades log (`trades[]`).
- `pending_actions.json` — actions awaiting Telegram approval (`actions[]`, status: `waiting`/`approved`/`rejected`). Virtual-portfolio entries use `type: sell|buy` + `market`/`reasoning`. Real-account entries (`AI_SUGGESTION_DRY_RUN` gate, added 2026-08-01) use a deliberately separate field set instead of overloading `type` — `action_type: sell|rebalance`, `target_account: "real"`, `market` (bare symbol, e.g. `"005930"`), `name`, `dry_run: true|false` — so `check_updates.py` can dispatch on `target_account` before ever touching the virtual-portfolio-mutating code that assumes `type`.
- `real_portfolio.json` — real Toss account snapshot (2026-08-01), written by `real_portfolio_sync.py`/`sync_real.yml`. `synced_at`, `cash` (KRW total, USD folded in via the live exchange rate), `positions[]` (`symbol`/`name`/`market_country`/`currency`/`quantity`/`avg_price`/`current_price`/`eval_amount`/`eval_amount_krw`/`return_pct`). **Deliberately excludes `accountNo`/`accountSeq`** — those exist only in-memory in `real_portfolio_sync.py` to build the `X-Tossinvest-Account` header and are never logged or persisted, since this repo is public. Read (not written) by `analyze.py` for the `AI_SUGGESTION_DRY_RUN` gate above.
- `last_report.json` — denormalized snapshot for `index.html`; kept in sync by both `analyze.py` and `check_updates.py`.
- `telegram_offset.json` — last processed Telegram `update_id`, owned by `check_updates.py`.

Both GitHub Actions workflows commit these files back to the branch after running (`git add ...; git commit; git push`), so the two workflows (`daily.yml` at 11:00 UTC, `poll.yml` every 5 min as of 2026-08-08) can race on the same files — be aware of that when changing commit/push logic or file schemas, since a schema change must stay compatible with whatever the other workflow's last commit wrote. `autoexec_state.json` specifically now has a third racer, `autoexec_stop_fast.yml` (also every 5 min) — both its commit step and `poll.yml`'s use the rebase+retry pattern from `sync_real.yml` for this reason.

`backtest_report.json` (repo root, written by `backtest.py`/`backtest.yml`) is a separate output, not part of the daily/poll state, so it doesn't participate in the race above — `backtest.yml` only ever commits it on its own schedule (manual `workflow_dispatch`), never racing `daily.yml`/`poll.yml`. It's read by `index.html` (2026-08-02 rebuild, see above) but that's a read-only fetch, not a write path, so it still can't race anything. Similarly `news_event_calibration_log.json` (written only by `news_event_experiment.yml`) is now also read by `index.html` — same read-only, no-race situation. `news_event_backtest_log.json` (2026-08-02, written only by `news_event_backtest.yml`, `workflow_dispatch`-only) is the **past-news backtest track's separate dataset** — see below.

**Phase 2 has two parallel, deliberately unmixed calibration tracks (2026-08-02).** The live/prospective one (`news_event_experiment.py` → `news_event_calibration_log.json`, daily cron) judges today's headlines and waits for D+1/D+5/D+20 to arrive. The retrospective one (`news_event_backtest.py` → `news_event_backtest_log.json`, `workflow_dispatch` only) replays Feb–Jul 2026 headlines whose outcomes already exist, so calibration numbers land immediately instead of waiting months. Selection criteria were **pre-registered before any collection** in `Phase2_과거뉴스백테스트_설계.md` (exhaustive/전수 over the same `KRX_MARKET_CAP_TOP` universe at a fixed trading-day stride — no random sampling, no outcome-based filtering) precisely so the results can't be dismissed as cherry-picked. The retrospective collector reuses `news_event_experiment.ask_news_event_judgment` verbatim (identical prompt, identical `JUDGE_MODEL`, and no `tools` parameter — the model has no way to look anything up), and hard-validates every RSS item's `pubDate` against the judgment window so a silently-ignored `after:`/`before:` operator produces zero samples rather than lookahead-contaminated ones. **Never merge or co-analyze the two datasets** — `news_event_calibration_analysis.py --log-file <file>` analyzes exactly one, and stamps `_meta.log_file`/`_meta.track` on its output. Critically, **a passing result on the retrospective track alone must not be treated as clearing the §2.1 gate**: if the judge model was trained on that period it can recall how the events resolved, a contamination that blocking tool access does nothing about and that the live track doesn't have (`Phase2_과거뉴스백테스트_설계.md` §4-1). Treat the retrospective track as a leading indicator; the live track remains the arbiter, and it keeps running untouched.

## Conventions specific to this repo

- User-facing strings (Telegram messages, report text, dashboard labels) and strategy-type values (`단타`/`스윙`/`장기`, `매수`/`매도`/`보유`/`비중조정`) are in Korean — keep new user-facing text and the JSON `action`/`strategy_type` vocabulary consistent with the existing Korean terms rather than switching to English.
- Claude is prompted to return *only* raw JSON; `ask_claude_decision` defensively strips code fences and extracts the outermost `{...}` before parsing, and retries once on failure. Preserve this defensiveness if you touch the prompt or parsing.
- Failures in price lookups, news fetches, or AI calls are caught and degrade gracefully (falling back to entry price, "뉴스 조회 실패", or an error message sent to Telegram) rather than crashing the workflow — the daily/poll Actions must keep running and committing state even when an external API is down.

## Working principles

- When you modify code, briefly explain *why* you changed it that way, not just what changed.
- Never remove or weaken the safety guardrails (hard stop-loss thresholds, the approval requirements for long-term/stock/large-position trades) as a side effect of an unrelated change. If a guardrail genuinely needs to change, call it out explicitly and confirm with the user first.
- Don't take this simulation toward real-money execution on your own initiative — that transition is a deliberate, separately-discussed decision gated on backtest results.
- **While the backtest gate (계획서 v3.1 §2.1) has not passed, do not add or re-enable a real-time external data connector (news APIs and similar — this explicitly includes anything in the `get_news_headlines` family) on your own judgment within a session.** Get sign-off in a direction-setting session (claude.ai) first, then connect it. This was written after `get_news_headlines` got wired into `ask_claude_decision`'s live approval flow without validation and had to be reverted same-day (PR#4) — see the Phase 2 news-events paragraph above.
- **Same category of mistake, recurring pattern (as tracked by the user, 3rd occurrence as of 2026-08-02): PR#10/#11 wired `real_portfolio.json` into `ask_claude_decision` (the "Real-account suggestion dry-run gate" work above) without a prior direction-setting-session approval** — the same procedural gap as PR#4 (a session extended what the live decision flow touches on its own judgment, not because it was unsafe in isolation).
