# Separate read-only operational audit

Verification-only control loop, not independent financial research review. The auditor does not import the execution engine. It opens the existing public duty SQLite store in read-only/query-only mode, reads a consistent snapshot, independently enumerates expected KST slots for up to 30 days, checks heartbeat, missing and expired work, source/child digest binding, stage completeness and ownership, blocked stages, report integrity, pending reviews, uncertain HQ delivery and unexpected AI reservations. A coverage boundary is persisted by the scheduler; migration from older stores begins verified coverage at migration, not invented historical coverage. A healthy audit is limited to this local workflow, not the entire organization.

The auditor writes only to a separate SQLite audit ledger, emits bounded fixed-code findings (no raw data or private values), exits 2 for exceptions, and cannot repair, retry, authorize, contact a provider or trade. A same-host account is not an independent security principal; a separate read-only process is not an independent research reviewer. Digest checks do not prove authenticity against an attacker able to rewrite both payload and digest. Retention, externally anchored hashes and stronger separation remain deployment gates.

15-minute timer (04,19,34,49 past each hour) is offset from the five-minute collector timer to reduce overlap. Templates are NOT installed; real SQLite WAL read-only compatibility and systemd verification on target Vultr remain required. Use reviewed pinned checkout, verify unit syntax, permissions, backup/restore, existing resource limits; activate only after public duty store exists. No automated outbound alerts yet: local journal and audit DB are the initial exception channel. Reporting to HQ must use separately reviewed fixed-code projection and authenticated transport. No external model calls or production changes.
